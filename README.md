# tender-ai — ИИ-платформа для поставщиков госзакупок

Два модуля (44-ФЗ / 223-ФЗ):

1. **Тендеры** — сервис сам забирает новые закупки из ГосПлан API под профиль компании, отсекает неподходящие жёсткими фильтрами, остальные оценивает нейросетью (соответствие профилю 0–100, причины, что проверить), показывает ленту и каждое утро присылает лучшие в Telegram.
2. **Разбор документации** — загружаете документы закупки (или нажимаете «Разобрать документацию» у закупки в ленте) — получаете карточку: условия, сроки, деньги, требования, штрафы, риски, вопросы для запроса разъяснений. У каждого значения — ссылка на файл, страницу и дословную цитату; цитаты проверяются по тексту.

3. **Выгодность** — для закупки сервис берёт товарные позиции из извещения (что, сколько, характеристики КТРУ, цена заказчика за единицу), находит в реестре контрактов ЕИС, почём такой же товар покупали за год, и считает экономику: цену победы после снижения на торгах, закупку, логистику, налоги, гарантии, замороженные деньги, **прибыль и маржу**, **максимальную цену, по которой можно покупать товар**, и **до какой цены снижаться на торгах**. В ленте — метка «выгодно / на грани / невыгодно», сортировка «Сначала выгодные».

Бизнес-модель, под которую это сделано: берём госзаказ, сами закупаем товар у продавца, сами везём заказчику, зарабатываем на разнице.

4. **Поиск поставщиков** — по кнопке в карточке закупки сервис для каждой позиции собирает предложения (прошлые госконтракты, поиск в интернете без рекламы, магазины из списка, ручные ссылки), сверяет товар с ТЗ, считает доставку до заказчика и успеваем ли к сроку, проверяет продавца по ЕГРЮЛ и подставляет лучшее предложение в расчёт прибыли.

5. **Перепродажа** (режим по умолчанию) — сервис сам ищет закупки, на которых можно заработать на разнице цен: товар любой, работы и услуги и лицензируемые товары отсекаются, остальное оценивается по потенциалу, считается ожидаемая маржа, и для лучших автоматически ищутся поставщики.

Дальше: запросы коммерческих предложений поставщикам, проверка заявки, CRM, кабинеты и оплата (как FinHelper).

## Поиск «как у людей»: фото из ТЗ и готовые запросы

Так ищут товар люди, которые зарабатывают на тендерах: прочитали ТЗ → нашли товар в Яндексе (текстом или по фото) → самый выгодный честный продавец.

- **Фото из ТЗ** (`server\extract\images.js`, `server\tenders\photos.js`): картинки из файлов Word в документации закупки (в том числе внутри ZIP). Отбрасываются логотипы и печати (меньше 15 КБ), векторные EMF/WMF, сканы страниц (крупные, с пропорциями листа А4/Letter) и картинки из обоснования цены, проекта контракта и форм заявки. Фото привязывается к позиции, наименование или модель которой стоит перед ним в тексте ТЗ. Хранятся в `data\photos\<id закупки>\`, отдаются `GET /api/tenders/:id/photos/:photoId`. Из PDF и старого .doc фото пока не извлекаются.
- **Ручной поиск без ключа**: у каждой позиции в карточке — фото из ТЗ и кнопки «Искать в Яндексе» / «в Картинках» с запросом, который сервис составил по ТЗ (модель, производитель, отличительные числа с единицами, без «или эквивалент» и голых чисел). Найденного продавца вставляете ссылкой в «Добавить предложение».
- **Автоматический поиск по фото** (источник `photo` в `OFFER_SOURCES`, нужен ключ Яндекса): фото позиции уходит в Yandex Search API `POST /v2/image/search_by_image`, найденные страницы открываются и сверяются с ТЗ как обычно. Запросы входят в тот же суточный лимит `SEARCH_DAILY_MAX_API_REQUESTS`.
- **Пробный прогон**: `npm run pilot` подбирает 20 выгодных закупок разных групп → `docs\pilot-candidates.md`; `npm run pilot -- --run` (с ключом Яндекса) сравнивает поиск по тексту и по фото → `docs\pilot-search-results.md`.

## Источники закупок (этап 6a)

`TENDER_SOURCES` — несколько источников сразу, через запятую и по порядку важности (по умолчанию `gosplan`):

| Источник | Что даёт | Условия |
|---|---|---|
| `gosplan` | закупки, извещения с позициями и ценами, реестр контрактов | тестовый сервер бесплатно (медленно, лимиты), боевой — по ключу |
| `eis-rss` | официальная лента поиска ЕИС: закон, номер, наименование, заказчик, НМЦК, дата | бесплатно и без ключа; пауза 60 с между запросами — требование robots.txt ЕИС |
| `fixture` | сохранённые закупки из `samples\tenders` | без сети, для тестов |

Одна и та же закупка из разных источников склеивается по «закон + номер извещения», пустые поля дополняются данными следующего источника (`server\sources\multi.js`). Документы, извещения и контракты берутся у первого источника, который это умеет и отвечает: лента ЕИС не содержит региона, срока подачи и кодов ОКПД2/КТРУ — их добирает ГосПлан. В ленте у закупки видно источник, список включённых — в «Профиле».

**Только закупки, на которые можно успеть.** Срока подачи в ленте ЕИС нет, поэтому она запрашивается с отбором: окончание подачи не раньше чем через «дней до подачи» из профиля; закупки не на этапе «Подача заявок» (отменённые, завершённые) в ленту не берутся, а уже попавшие к нам — убираются из неё (`closed_stage`). Отбор по этапу (`af=on`) не ставится намеренно: отменённые закупки со сроком в будущем нужны, чтобы их убрать. Прежний вариант — этап «Подача заявок» и окончание подачи не раньше чем через «дней до подачи» из профиля (`applSubmissionCloseDateFrom`, по умолчанию 2). Каждая закупка из ленты получает нижнюю границу срока `deadline_from` («окончание не раньше этого дня»); точный срок дозагружается из извещения. В ленте — закупки, у которых точный срок или эта граница не раньше начала московских суток «сегодня + N дней»; закупка из ленты ЕИС без того и другого не показывается. Повторно найденная закупка не затирает пустыми полями ленты то, что уже известно из извещения (срок, регион, коды). Кроме того, после каждого обновления ленты сервис сверяет этап закупок из ленты с ЕИС по номеру (`getStage`, по `STAGE_CHECK_PER_SYNC` = 10 за проход, каждую — не чаще раза в `STAGE_CHECK_HOURS` = 24 ч; сначала закупки из корзины и самые выгодные): отменённые и закрытые уходят из ленты, даже если их срок ещё не прошёл. Тесты — `test/feed-deadlines.test.js`.

Разбор всех сервисов поиска тендеров (Контур.Закупки, Тендерплан, Ростендер, СБИС, Seldon, Интерфакс, площадки) — что бесплатно, что платно и что запрещено правилами сайтов: **`docs\sources-review.md`**.

## Режим «Перепродажа» (этап 5)

Переключатель — «Профиль → Режим поиска закупок» (`mode: resale | profile`, поле профиля). В режиме «По профилю» всё работает как на этапах 2–4.

**Воронка** (после каждой синхронизации, `server\tenders\funnel.js`):

1. **Жёсткие фильтры без нейросети** (`server\tenders\filters.js` `resaleReason()`, правила — `config\resale-exclusions.json`): только поставка товаров (разделы ОКПД2 01–33 и печатные издания; без кодов — по словам «работы», «услуги», «ремонт», «монтаж»…); без лекарств, алкоголя и спирта, оружия и взрывчатки, наркотических и прекурсоров, драгметаллов. Коды и ключевые слова профиля в этом режиме не сужают загрузку. Регионы, НМЦК, стоп-слова и срок до подачи — как раньше.
2. **Оценка потенциала** нейросетью облегчённой моделью (`resale-score.md`, task `resale_score`): массовый ли товар, нет ли монтажа и сервиса, заточки под поставщика, растянутой на год поставки.
3. **Ожидаемая маржа** для лучших `RESALE_ECONOMICS_PER_SYNC` по оценке: цена закупки — 25-й перцентиль прошлых контрактов (если сопоставима с ценой заказчика), доставка — от ближайшего узла `RESALE_HUBS` (Москва, Санкт-Петербург, Екатеринбург, Новосибирск, Краснодар) до региона заказчика, плюс снижение на торгах, налоги и обеспечения (тот же калькулятор этапа 3).
4. **Ранг возможности** (`server\tenders\opportunity.js`): подтверждённая поставщиками прибыль → ожидаемая маржа × уверенность (доля суммы, оценённая по контрактам, и их число, 5+ — полная) + оценка × 0,1 → без маржи. Сортировка ленты по умолчанию — «Сначала выгодные» (`sort=opportunity`).
5. **Автопоиск поставщиков** для лучших `RESALE_AUTO_SEARCH_PER_SYNC` закупок с маржой ≥ `RESALE_MIN_MARGIN_PCT`, где поиска ещё не было.

**Поиск поставщиков в этом режиме шире:** до `SEARCH_MAX_QUERIES_PER_ITEM` (5) запросов на позицию — артикул/модель, название + характеристики, «оптом», «дистрибьютор», «с НДС», город заказчика; B2B-каталоги из `config\stores.json` (`b2b`: Пульс цен, Supl.biz, Flagma) — запросом `site:…` через тот же Яндекс Search API; не больше `SEARCH_MAX_PAGES_PER_DOMAIN` (2) страниц с одного сайта; маркетплейсы и доски объявлений в стоп-списке. Суточный лимит платных запросов — `SEARCH_DAILY_MAX_API_REQUESTS` (200, учёт в базе), дальше — только бесплатные источники.

**Проверенный продавец** (метка в таблице, первый ключ сортировки после вашей отметки): ИНН известен (на сайте или из реестра контрактов), действует по ЕГРЮЛ 3+ лет, уже выигрывал госконтракты. Репутация ИНН копится в таблице `sellers` между поисками.

## Подбор товара строго по ТЗ (этап 6b)

Проблема, которую решает этап: под одним кодом ОКПД2/КТРУ в прошлых контрактах — разные товары (картриджи от 87 до 16 600 ₽), поэтому маржа считалась «по чужому товару», а поставщики подбирались приблизительно.

- **ТЗ читается автоматически.** Воронка (`server\tenders\funnel.js`) для самых перспективных закупок (маржа ≥ `RESALE_MIN_MARGIN_PCT` или неизвестна при оценке ≥ 70) сама скачивает документацию и разбирает её — не больше `RESALE_DOCS_PER_SYNC` (10) за синхронизацию и `RESALE_DOCS_PER_DAY` (20) в сутки, чтобы не тратить бесплатный пакет GigaChat Max. В карточке — кнопка «Прочитать ТЗ» для любой закупки; по окончании любого разбора документации спецификация читается сама.
- **Спецификация** (`server\analyze\prompts\spec.md`, task `spec`): по каждой позиции — обязательные характеристики с условием («не менее 80 г/м2»), модель, производитель, совместимость, ГОСТ, разрешён ли эквивалент, фасовка. Каждое требование — с цитатой, файлом и страницей; цитата проверяется по тексту (`verify.js`). Хранится в `tender_items.spec_json`, дополняет позиции извещения (непустые характеристики извещения не затираются).
- **Тот же товар** (`server\offers\spec.js` `sameProductDet`): модель/артикул, формат (А4 ≠ А3), числа с единицами (80 г/м2 ≥ 80), латинские буквы-двойники. Прошлые контракты хранят строки с наименованием и характеристиками КТРУ (`benchmarks.data_json.lines`); в ориентир цены (`server\tenders\item-benchmark.js`) идут только строки «тот же товар». Неясные строки сверяет облегчённая модель (`same-product.md`, task `same_product`). Точная позиция каталога КТРУ без требования модели — тот же товар.
- **Единицы** (`server\offers\units.js`): шт ↔ упак/пачка по фасовке, кг ↔ т, л ↔ м³, л ↔ т по плотности (топливо), коды ОКЕИ. Неизвестный пересчёт — «несопоставимо».
- **Поиск по отличительным признакам**: запросы из спецификации — модель с производителем, затем наименование + числа с единицами, совместимость.
- **Строгая сверка**: в расчёт прибыли автоматически идёт только «соответствует» (все ключевые требования подтверждены и ни одно не противоречит). «Частично» и «не хватает данных» остаются в списке с пометкой «спросите у продавца».
- **Качество**: `npm run eval:match` — набор реальных пар «позиция ТЗ ↔ товар из контракта» (`test\fixtures\match-eval.json`), доля «другого товара» среди выбранных и полнота «до/после»; `-- --llm` — с нейросетью.

## Профильные компании: запросить цену

У дистрибьюторов и оптовиков оптовой цены на сайте нет — её дают партнёрам, прайсом или коммерческим предложением. Такие компании сервис показывает в карточке закупки под каждой позицией отдельным списком «Профильные компании: запросить цену»: это **кандидаты, а не предложения** — в расчёт выгодности они не входят и закупочной цены не имеют, пока вы сами не получите цену и не впишете её в «свою цену».

- Каталог: `config/profile-suppliers.json` (12 компаний с источником сведений и способом получения цены; `SUPPLIER_CANDIDATES_CONFIG`) плюс уже известные сайты из `config/stores.json` (`distributors`, `suppliers`); записи с одним сайтом склеиваются (`server/offers/supplier-catalog.js`). Юрлица, цены и условия не проверялись.
- Подбор — по направлению позиции (оргтехника, сеть, видеонаблюдение, компьютеры), не по наличию модели.
- «Состояние» — отметка пользователя (контакт не установлен / запрос подготовлен / ожидается ответ / условия получены), хранится в настройках базы (`supplier_candidate:<сайт>`), на расчёт не влияет.
- **Товар и цена прямо в блоке.** У компаний с открытыми ценами (`access_mode: public_site` — магазины из `config/stores.json`) показано, что сервис нашёл на их сайте по позиции: название со ссылкой, цена, наличие, итог сверки (`attachProducts` в `server/offers/supplier-catalog.js`). Если по позиции у компании ничего нет, страница товара ищется в своём каталоге страниц поставщиков по модели из ТЗ или по моделям уже подошедших товаров и читается как при поиске — бесплатно (`lookupCandidates` в `server/offers/index.js`, `POST /api/tenders/:id/supplier-candidates/lookup`). Поиск поставщиков делает это сам в конце (`SEARCH_CANDIDATE_LOOKUPS`, 12 страниц), остальное — в фоне, пока открыта карточка. Итог «модели на сайте нет» помнится 3 дня или до нового поиска. Найденное — обычные предложения: они стоят в таблице «Где купить» и участвуют в расчёте.
- «Подготовить запрос КП» — текст письма с требованиями ТЗ для копирования. Сервис ничего не отправляет и на сайтах компаний не регистрируется; новых сайтов в обход страниц модуль не добавляет.
- API: `GET /api/supplier-candidates?direction=office|network|cctv|computers`, `PUT /api/supplier-candidates/:site` `{status, note}`, `GET /api/tenders/:id/supplier-candidates/:site/rfq?item_id=ID`.

Позиции закупки при повторной загрузке сохраняют id, свою цену, выбранное предложение и прочитанное ТЗ, если их содержание не изменилось (`saveItems`); изменившаяся позиция — новая строка без прежних цен. Расчёт выгодности при этом сбрасывается и считается заново. Выбранное предложение повторный поиск не удаляет; у предложения с неполной сверкой или старой ценой интерфейс показывает «проверьте».

## Путь по закупке: от документов до итога

Карточка закупки разбита на четыре шага с кнопками «Назад» и «Далее»: **Документация → Поставщики → Расчёт → Итог**. Шаг виден в адресе (`#tender/ID/docs|suppliers|calc|summary`) и сохраняется при обновлении; перейти дальше можно и с незавершённым шагом — под шагами написано, чего не хватает.

- **Правовой вывод** (`server/analyze/legal.js`, промпт `legal.md`). После разбора документации — блок «Соответствие закону»: спорные условия со ссылкой на документ, нормой и предлагаемой редакцией. Числовые нормы 44-ФЗ (срок оплаты, обеспечения заявки, контракта и гарантии, односторонний отказ) проверяет код; остальное — нейросеть, но ссылаться она может только на нормы из `config/legal-norms.json` и только по теме замечания. Перечень сверен с текстом закона (дата — в файле); нормы не из перечня помечаются «требует проверки юристом». Итог: «замечаний нет», «направить обращение» или «отказаться от участия» (серьёзное условие, а срок запроса разъяснений истёк). Для 223-ФЗ и коммерческих закупок перечень не составлен. Это предварительная проверка, не юридическое заключение.
- **Письмо заказчику** «О спорных вопросах и предложениях по их разрешению»: адресат — контактное лицо заказчика из извещения (`server/tenders/customer.js`), по каждому условию — довод, норма, редакция; срок подачи запроса. `GET /api/analyses/:id/letter`, `…/letter.md`; сервис письмо не отправляет. Проверить заново — `POST /api/analyses/:id/legal`.
- **Количество в наличии** (`server/offers/stock.js`): берётся первая пометка о наличии возле названия товара — число («в наличии 12 шт», «1 000+ м», «от 1 до 3»), иначе слово; остатки «похожих товаров» ниже по странице не читаются. Наличие всегда одно из трёх: «в наличии», «нет в наличии», «под заказ» (или пусто, если магазин его не показывает). Числа из служебных данных страницы (`data-quantity`, `max` у поля количества) не берутся — у большинства сайтов это не остаток; исключение — сайты с проверенным атрибутом (`stock_attr` в `config/stores.json`). У находок до 09.10.2026 остаток дочитывается повторным открытием страниц (`POST /api/tenders/:id/offers/stock`, без поисковика и нейросети). Как каждый из 33 поставщиков показывает остаток — `docs/supplier-search-losses.md`.
- **Набор партии** (`server/offers/allocate.js`, таблица `item_allocations`): у лучшего подходящего продавца берётся сколько есть, остаток — у следующих; набор правится вручную (`PUT /api/tenders/:id/items/:itemId/allocations`). В расчёт идёт сумма набора и доставка от каждого продавца; не закрытая полностью партия цены в расчёт не даёт. Выбор одного предложения на всё количество — частный случай.
- **Логистика** (`server/offers/logistics.js`, `cargo.js`, `config/logistics.json`): сначала доставка продавца, если он назвал её цену; иначе перевозчик по тарифной сетке — по весу и объёму партии (со страницы товара или оценка по виду товара); иначе оценка по расстоянию. Сетка СДЭК подогнана 09.10.2026 под расчёты на сайте перевозчика (склад → дверь, три маршрута: сборный груз 1 м³ и посылка 10 кг / 0,05 м³; у посылок до 30 кг свои сроки — `parcel`); ПЭК и «Деловые линии» выключены (`enabled: false`), пока их цифры не подтверждены. **Это оценка по сетке, не расчёт перевозчика.** Калькуляторы СДЭК, ПЭК и «Деловых линий» по API не подключены: нужны договоры и ключи.
- **РНП** (`server/offers/rnp.js`): продавцы из предложений проверяются по реестру недобросовестных поставщиков ЕИС автоматически — в фоне, после каждого поиска и обновления ленты (`RNP_AUTO`, `RNP_CHECK_PER_SYNC`, перепроверка раз в `RNP_RECHECK_DAYS` дней). robots.txt ЕИС это разрешает (`Allow: /*dishonest*`) с паузой 60 с — очередь запросов к ЕИС общая с лентой поиска (`server/sources/eis-gate.js`). Совпадение ИНН — только точное, считаются действующие записи («Размещено»); исключённые показываются как «раньше был в реестре». Страница не распознана (сайт изменился, проверка «я не робот») — отметка не меняется, проверку «я не робот» сервис не обходит. Своя отметка пользователя (`POST /api/sellers/:inn/rnp`) важнее автоматической, кроме найденной действующей записи; проверить вне очереди — `POST /api/sellers/:inn/rnp/check`. «В реестре» — продавец сам в расчёт не идёт.
- **Отбор ленты по марже**: в профиле «Показывать закупки с маржой от, %» (по умолчанию 20, 0 — выключено; `PUT /api/profile/feed`, переоценку не запускает). Закупки без расчёта остаются в ленте; `GET /api/tenders?min_margin=N` возвращает `hidden_by_margin`.
- **Итог**: что и у кого покупаем (продавец, город, контакты, цена, сумма), логистика, заказчик и место поставки (`GET /api/tenders/:id/customer`), сроки, ссылки на разбор и письмо, выгодность. Печатается без меню и кнопок.

## Полное чтение документации и решение об участии

Документация читается целиком, а что прочитать не удалось — видно и мешает считать вывод окончательным. Подробности и цифры по сохранённым разборам — `docs/full-reading-report.md`.

- **Полнота** (`server/analyze/coverage.js`): у каждого файла — версия (`sha256`) и отчёт об извлечении (`files.coverage_json`: ожидалось / обработано / пустые / непрочитанные страницы с причиной); у разбора — `card.meta.coverage`: загрузка → извлечение → отправка фрагментов → принятые ответы. Дробь показывается, только когда знаменатель известен.
- **Сканы** (`server/extract/ocr.js`): распознаются все страницы партиями; `OCR_MAX_PAGES` — бюджет одного прохода, остаток остаётся в отчёте и дочитывается. Пустой лист отличается от страницы-изображения. Картинки внутри Word распознаются.
- **Фрагменты** (`server/analyze/chunk.js`, `queue.js`, таблица `analysis_chunks`): все страницы всех файлов; длинная страница делится по абзацам с перекрытием; принятый результат хранится по ключу «задача + версия промпта + модель + текст» и не запрашивается повторно; не справившийся с объёмом запрос делится пополам.
- **Ответы нейросети** (`server/analyze/json.js`): оборванный лимитом ответ (`finish_reason: length`) не принимается; обязательные ключи; пустой результат — только с `"result": "nothing_found"`; виды сбоя: `transport`, `quota`, `too_large`, `truncated`, `filtered`, `invalid_json`, `schema`, `unconfirmed`.
- **Решение** (`server/analyze/decision.js`): `card.decision` — `analysis_status` (complete / incomplete / needs_review / failed), `decision_status` (final / preliminary), `participation_recommendation` (в том числе «недостаточно данных»), причины с источником и действием. Нейросеть даёт кандидата, окончательность определяет код.
- **Позиции и ТЗ** (`server/tenders/details.js`): читаются по всей документации, отчёты `tender_details.items_coverage_json` и `spec_coverage_json` (со сверкой состава и количеств). При пробелах расчёт помечается `result.preliminary` с перечнем `spec_gaps`.
- **Повтор и ручная проверка**: `POST /api/analyses/:id/retry` — дочитать непрочитанное; `POST /api/analyses/:id/gaps` `{key, confirmed}` — пробел проверен человеком.
- **Сверка по сохранённым разборам**: `node scripts/reading-coverage-report.js --data <папка с app.db> [--top N] [--summary]`.

### Противоречия со ссылками на документ

Если условие в разных документах указано по-разному, у каждого значения есть кнопка «открыть в документе»: открывается страница файла с подсвеченной цитатой. Так показаны причины решения в разборе и блок «Противоречия в документах / Спорные условия / Риски» на шаге «Документация» карточки закупки. «Значение» без источника (нейросеть написала «не указано» и не назвала ни файла, ни цитаты) противоречием не считается: в новые разборы оно не попадает (`server/analyze/merge.js`), а из готовых убирается при запуске сервера с пересчётом решения правилами (`cleanConflicts`).

### Перечитывание без кнопки

Готовый результат не оставляется как есть в двух случаях: разбор сделан прежней версией сервиса (в карточке нет отчёта о полноте) или упал по временной причине — ЕИС не отдал файлы, у нейросети кончился запас, оборвалась связь (`server/tenders/reread.js`).

- **При открытии карточки закупки** сервис сам запускает чтение заново и говорит об этом. Только для закупок с непрошедшим сроком подачи, не больше `REREAD_ON_OPEN_PER_DAY` (15) в сутки и не чаще раза в `REREAD_RETRY_HOURS` (6) часов по одной закупке. `REREAD_ON_OPEN_PER_DAY=0` — выключить.
- **В фоне после обновления ленты** — в пределах обычного лимита разборов (`RESALE_DOCS_PER_SYNC`, `RESALE_DOCS_PER_DAY`): сначала закупки с предложениями в корзине, затем новые закупки, затем остальные устаревшие и упавшие.
- Новый разбор не удался, а прежний был готов — закупке возвращается прежний разбор.
- **Что не считается пробелом:** файлы подписи и сертификаты (в том числе у разборов прежней версии — по расширению) и печатные копии (`server/extract/renditions.js`): «ТЗ.docx.pdf» рядом с «ТЗ.docx» с тем же текстом не читается второй раз — запросов к нейросети вдвое меньше.
- **Нейросеть отказалась отвечать на фрагмент** (фильтр провайдера) — фрагмент делится пополам до трёх раз: непрочитанной остаётся только малая часть с этим местом (`server/analyze/queue.js`).

Тесты — `test/reread.test.js`.

## Читатель по правилам

Позиции закупки и требования ТЗ сначала читаются без нейросети — из таблиц документов (`server/extract/tables.js`, `server/tenders/rule-items.js`). Таблицы Word и листы Excel сохраняются в тексте построчно: ячейки через « | », продолжение объединённой по вертикали ячейки — «″». Правила находят шапку («Наименование товара», «Кол-во», «Ед. изм.»), читают позиции и их характеристики (строками под позицией, в соседней ячейке или в отдельной таблице характеристик), у каждой характеристики — цитата и страница. Список берётся из одного, самого подходящего файла (ТЗ → прочие → обоснование цены). Нестандартную таблицу правила не угадывают — такие документы читает нейросеть. Сравнение с моделями на настоящих закупках — `docs/full-reading-report.md`.

## Подготовка заявки (основа)

Шаг «Заявка» в карточке закупки (`#tender/ID/bid`, `server/bids/`). Сервис ничего не подаёт и не подписывает.

- **Сценарий** (`classify.js`): закон, способ, электронная ли форма, только ли для МСП — по извещению источника, разбору документации и названию. Поддержаны `44_eauction`, `44_equotation`, `44_ecompetition`, `223_sme_*`, `223_other_competitive`; ЕАТ, закупка у единственного поставщика, закрытые и неэлектронные — явное «не поддерживается». Неизвестный признак остаётся неизвестным, расхождение источников — блокирующий конфликт.
- **Правила состава** (`config/bid-rules/*.json`, `rules.js`): версионированный набор с отпечатком; все правила — черновики, пока человек не отметит «сверено» (`POST /api/bid-rules/:id/verify`); отметка действует для этого отпечатка набора.
- **Реестр требований** (`requirements.js`): записи из правил сценария и из документации (требования ТЗ к каждой позиции с документом, его хешем, страницей и цитатой; условные требования — по разбору; состав заявки по документации заказчика).
- **Проверка** (`validate.js`): несостыковки с обеими сторонами расхождения и действием; товар, у которого найдено другое значение, — блок, который решением проверяющего не снимается; совпадение на странице продавца — кандидат, а не доказательство.
- **Готовность** (`readiness.js`): статус пакета (`draft / needs_input / needs_review / blocked / prepared_for_transfer / transfer_verified / stale / unsupported`), три оси, девять условий, счётчики.
- **Устаревание**: проверка привязана к отпечатку входных данных; изменились документы, товар, цена или срок — статус `stale`, подтверждения человека не действуют.
- **Маршруты**: `POST|GET /api/tenders/:id/bids`, `GET /api/bids/:id`, `POST /api/bids/:id/validate|attestations|review-decisions`, `GET /api/bid-rules`.
- **Анкета участника** (`dossier.js`, вкладка «Профиль»): кто подаёт заявки — ИП или организация; реквизиты вводит сам участник, сервис проверяет формат и контрольные разряды (ИНН, ОГРНИП, ОГРН, БИК, счёт). У ИП нет полей и документов организации; паспортные данные не запрашиваются. Маршруты `GET|PUT /api/dossier`.
- **Документы участника**: файл хранится без изменений в `DATA_DIR/uploads/dossier-<id>/` с `sha256`, у документа — вид, даты выдачи и окончания действия, отметка «проверено мной». Замена файла — новая запись, прежняя в архиве. Маршруты `POST /api/dossier/documents`, `PUT|DELETE /api/dossier/documents/:id`, `GET …/download`.
- **Список «что приложить»** (`checklist.js`, шаг «Заявка»): по каждому применимому требованию — что требуется, откуда (документ заказчика со ссылкой на место или правило сценария), чем закрывается (документ участника, сведения анкеты, реестр участников, заявление, товар, цена, действие на площадке) и состояние: «есть», «нет», «срок истёк», «истечёт до окончания подачи», «нужно подтвердить», «не требуется», «к сведению». Документы, которые заказчик называет в составе заявки, узнаются по словам и подбираются из хранилища по виду и сроку действия на день окончания подачи. Человек может выбрать другой документ или отметить «не требуется» с причиной (`POST /api/bids/:id/checklist`) — вывод сервиса сохраняется.
- Условие готовности «проверены участник и товары» выполняется, когда анкета заполнена, регистрация в реестре участников и обязательные документы действуют и проверены, а показатели выбранных товаров подтверждены. Анкета и документы входят в отпечаток входных данных: изменились — заявка `stale`.
- **Файлы заявки** (`package.js`, `docx-writer.js`): составляются только под требования закупки и раскладываются по частям заявки по сценарию (`partFor`): по 44-ФЗ сведения об участнике файлом не подаются, цена в аукционе — на торгах; в закупках для малого бизнеса по 223-ФЗ товар идёт в первую часть, участник — во вторую, цена — отдельно. Значения — из анкеты, проверенных документов, выбранного товара и утверждённой цены; неизвестное — метка `[ЗАПОЛНИТЬ: …]`. DOCX собирается своим кодом, без новых зависимостей; показатели дублируются в XLSX. Формы заказчика (узнаются по имени файла) и оригиналы участника кладутся без изменений.
- **Цена**: `POST /api/bids/:id/price` — утверждается «своя цена» с шага «Расчёт»; рекомендуемая сама не подставляется; изменилась цена — утверждение не действует.
- **Декларация**: положения — в `config/bid-declarations.json` (черновик, не сверен с законом); подтверждаются каждое отдельно (`statements` в `POST /api/bids/:id/attestations`). Файлом декларация составляется, только если так требует закупка; иначе это действие на площадке.
- **Повторное чтение** (`verifyFile`): каждый составленный файл читается обратно тем же `server/extract` — потерянная строка, подпись без значения, оставшаяся метка, сведения об участнике в неподходящей части; у оригиналов сверяется `sha256`. От результата зависит условие готовности `postcheck`.
- **Выгрузка**: `POST /api/bids/:id/draft` — собрать версию (файлы в `DATA_DIR/bids/case-<id>/v<N>/`), `GET /api/bids/:id/files/:fileId`, `GET /api/bids/:id/export[?final=1]` — ZIP: `application-transfer/` (файлы по частям, `etp-fields.json|csv`, `transfer-checklist.md`, `manifest.json` с `sha256` и отпечатками) и `review-internal/`. Черновик выгружается всегда, с пометкой «ЧЕРНОВИК»; итоговый — только при выполненных условиях готовности, иначе ответ 409 со списком причин. Закупочных цен, прибыли и данных поставщика в `application-transfer/` нет.
- Извещение закупки запрашивается у источника по «Проверить заново» и при открытии дела; остальные действия берут его из памяти (30 минут) — чтобы не ждать очередь запросов к ЕИС.
- **Ещё не сделано**: адаптеры площадок (форматы, размеры, поля конкретной ЭТП), сверка фактического переноса, проверки по реестрам через сеть, автоматическое заполнение форм заказчика, структура заявки на конкурс по 44-ФЗ. Поэтому статус «подготовлена к переносу» пока недостижим — доступна выгрузка черновика.

## Закупка из своих документов (например, с ЕАТ «Берёзка»)

Для закупок, которых нет в ленте: владелец сам скачивает документы заказчика на площадке и загружает их — «+ Добавить закупку вручную» в ленте (`#add-tender`). Дальше закупка идёт обычным путём: Документация → Поставщики → Расчёт → Итог. К площадке сервис не обращается и ничего на неё не отправляет (`server/tenders/manual.js`).

- **Добавление**: `POST /api/tenders/manual` (multipart: `files[]` и поля `platform`, `number`, `title`, `price`, `deadline_at`, `region`, `customer_inn`, `url`, `text`). Обязательны только файлы или `text` — текст, скопированный со страницы закупки (сохраняется как ещё один файл). Закупка записывается с `source = 'manual'`, вне ЕИС (`law = 'com'`); номер ЕАТ — `EAT-<номер>`, как его запишет подключение площадки (ветка `eat-source`), без номера — `MANUAL-<дата>-<n>`. Тот же номер второй раз — ответ 409 со ссылкой на первую закупку.
- **Поля из документов**: что владелец не вписал, после разбора берётся из карточки разбора (предмет, цена, срок подачи, ИНН и название заказчика, место поставки, регион) и помечается «из документов — проверьте»; правка — блок «Данные закупки» на шаге «Документация» (`PUT /api/tenders/:id/manual`). Номер не меняется.
- **Файлы** лежат в `uploads/manual-<id>/` и переживают повторные разборы: «Разобрать заново» читает их, а не источник; «Добавить файлы» (`POST /api/tenders/:id/files`) дозагружает документы и собирает позиции из документов заново — та же позиция (то же количество, почти то же название) остаётся прежней записью с ценами и поставщиками (`keepKnown` в `server/tenders/details.js`).
- **Синхронизация** такие закупки не проверяет по фильтрам профиля и не оценивает; источник не перезаписывает закупку с тем же номером. В ленте — отметка «добавлена вручную» и отбор «только добавленные вручную» (`GET /api/tenders?manual=1`, показывает и скрытые, и с истёкшим сроком).
- **Удаление**: `DELETE /api/tenders/:id` — только для ручных закупок; вместе с файлами, разборами, предложениями и расчётом.
- **Ограничения**: правовая проверка по перечню норм 44-ФЗ для таких закупок не выполняется (закупка записана как «вне ЕИС»), снижение цены на торгах берётся из профиля; об изменениях на площадке сервис не узнаёт.

## Где теряются результаты поиска

- **Воронка поиска** (`server/offers/funnel.js`, колонка `offer_searches.funnel_json`): по каждой позиции — какие запросы ушли в Яндекс и сколько адресов вернулось, сколько отсеяно до открытия и почему (маркетплейсы, розничные сети, сайты, закрытые для программ, зарубежные, лишние ссылки с одного сайта, лимит страниц), сколько страниц открыто и почему страница не дала цены, итог сверки. В карточке закупки — «Куда делись результаты поиска».
- **«Простой» запрос** (`plainQuery` в `server/offers/sources/yandex-search.js`): последним на позицию уходит запрос «как у человека» — наименование и модель или две-три главные характеристики, без «купить» и «оптом». Плюс один платный запрос на позицию, если лимит не израсходован; `SEARCH_PLAIN_QUERY=0` выключает. С одного сайта открывается до трёх страниц (`SEARCH_MAX_PAGES_PER_DOMAIN`), на позицию — до 24 (`SEARCH_MAX_PAGES_PER_ITEM`).
- **Проверить ссылку** (`POST /api/tenders/:id/offers/check-url`): адрес товара, найденного руками, проходит те же шаги и получает ответ, на каком он теряется. Платных запросов не тратит, ничего не сохраняет; добавить товар — прежним ручным предложением.
- **Взаимоисключающие признаки** (`server/offers/traits.js`, `config/exclusive-traits.json`): чёрно-белая или цветная печать. Признак определяется по требованию ТЗ о нём самом (а не по словам «черно-белая печать» в других требованиях), у товара — по характеристикам страницы и названию, с синонимами. Противоречие — «не соответствует»; совпадение по синониму подтверждает требование. Учитывается в подборе моделей, отборе со страниц каталогов и сверке. Новый признак — запись в файле, без правки кода.
- **Разбор потерь на копии базы**: `node scripts/search-losses.js --data <папка с копией> --label before --tenders <id,…>` и `--report before after`. Ответы Яндекса запоминаются — повторный прогон с теми же запросами бесплатен; `--max-requests` — потолок платных запросов.

## Площадки закупок

Источник (откуда сервис узнал о закупке: ГосПлан, лента ЕИС, Росэлторг) и площадка (где идут торги и куда подавать заявку: Сбербанк-АСТ, РТС-тендер, Росэлторг, ЭТП ГПБ…) — разные вещи. Площадка названа в извещении 44-ФЗ (`commonInfo.ETP`) и в закупке 223-ФЗ (`electronicPlaceInfo`), в списках её нет. Сервис записывает её при загрузке подробностей закупки и дозаполняет в фоне после каждого обновления ленты (`PLATFORM_FETCH_PER_SYNC`, по умолчанию 30 закупок; сразу для всей ленты — `POST /api/platforms/fill`). Имена приводятся к коротким (`server/tenders/platforms.js`). В ленте — кнопка «Площадки» с двумя вопросами: где закупка опубликована (ЕИС — все госзакупки по 44-ФЗ и 223-ФЗ, каким бы путём сервис о них ни узнал; вне ЕИС — коммерческие) и на какой площадке идут торги. Отметки внутри вопроса складываются, вопросы сужают друг друга; счётчики считаются в пределах отмеченного в соседнем вопросе. Запросы: `GET /api/tenders?published=eis,com&platforms=A|B`, `GET /api/platforms`. Выбор запоминается в браузере.

## Поиск поставщиков (этап 4)

**Источники** (`OFFER_SOURCES`, модули в `server\offers\`):

| Источник | Что даёт | Что нужно |
|---|---|---|
| Прошлые госконтракты | Кто уже поставлял такой товар госзаказчикам, по какой цене, ИНН и адрес | ничего (данные этапа 3) |
| Поиск в интернете | Яндекс Search API: обычная выдача **без рекламных блоков**; сервис открывает найденные страницы и извлекает цену | `YANDEX_SEARCH_API_KEY`, `YANDEX_FOLDER_ID` — ключ сервисного аккаунта Yandex Cloud с ролью на Search API (платно, цены — на сайте Yandex Cloud) |
| Магазины | Прямой поиск на сайтах из `config\stores.json` | список сайтов; добавить магазин — новая запись с `searchUrl` (`{q}` — запрос) и `productLinkPattern` |
| Каталог оптовых поставщиков | Свой указатель «модель → страницы товара у поставщиков»: раз в неделю сервис читает карты сайтов (sitemap.xml) оптовых и оптово-розничных поставщиков из `config\stores.json` → `suppliers` и по модели находит товар сразу у всех — **бесплатно, без поисковика** | ничего; база — `<DATA_DIR>\suppliers.db` (≈0,6 ГБ), собирается сама через минуту после запуска. Сразу: `node scripts/build-supplier-index.js`; у кого есть модель: `… --find ST8000NE0001`; выключить: `SUPPLIER_INDEX=0` |
| Вручную | Ссылка на товар (сервис сам найдёт цену) или цена руками | — |

**Кого ищем.** Нужны поставщики с ценой ниже рынка, поэтому крупные розничные сети (`stores.json` → `retail`: Ситилинк, DNS, М.Видео…) в поиск не идут: их страницы не открываются, старые находки помечены и в расчёт не берутся. Дистрибьюторы (`stores.json` → `distributors`: Merlion, OCS, Treolan, Netlab…) показывают цены только после регистрации компании — сервис их не читает; список — для справки. Проверка 05.10.2026 (116 площадок с сервера): открытые цены и карта сайта есть у 33 поставщиков, они и стоят в `suppliers`.

**Порядок поиска по кнопке:** 1) читается ТЗ из документации закупки, если она ещё не разобрана; 2) определяется модель (из ТЗ или подбор под требования); 3) модель ищется в каталоге оптовых поставщиков; 4) платные запросы к Яндексу — в пределах лимитов; 5) каждая страница сверяется с ТЗ по каждому требованию; 6) «дожим»: подошедший товар ищется у остальных поставщиков каталога (`SEARCH_SWEEP_PAGES`).

Проверено 19.09.2026: у крупных магазинов прямой поиск по сайту почти везде закрыт для программ — robots.txt (Регард, ЧИП и ДИП), подгрузка результатов скриптом (НИКС), перенаправления и капча (Комус, Ситилинк, ВсеИнструменты, DNS). Сервис это соблюдает и пишет причину в журнал поиска. Поэтому основной источник — поисковый API: он находит карточки товаров, а их сервис открывать может, если сайт не запрещает.

**Как считается:**
- цена со страницы — из разметки schema.org (надёжнее), иначе нейросетью (промпт `server\analyze\prompts\offer.md`); цена за упаковку пересчитывается на единицу заказчика;
- соответствие ТЗ — по каждому требованию отдельно: нейросеть (`match.md`) отвечает «да / нет / не указано», числа сервис пересчитывает сам с переводом единиц; «соответствует» — нет противоречий и подтверждено каждое требование (ТЗ и извещение вместе; совпавшая модель остальные требования не заменяет), «частично» — подтверждена часть; подтверждением считается только то, что дословно или числом есть на странице; при более чем 45 требованиях сверяются первые 45, и «соответствует» такой товар не получает; таблица сверки видна в карточке; «не соответствует» уходит вниз с причиной;
- в расчёт прибыли само идёт самое дешёвое из «соответствует», кроме: нет в наличии, уценка / б/у, цена вдвое ниже обычной для этой позиции, розничная сеть — такие предложения остаются в списке с пометкой;
- доставка — если продавец указал срок/стоимость, берутся они; иначе оценка: расстояние между центрами регионов × 1,3, скорость и минимальная стоимость — в «Профиль → Экономика». Подключение ТК (СДЭК, ПЭК…) — заготовка `carriers` в `server\offers\logistics.js`;
- продавец — ИНН со страницы (с проверкой контрольной суммы) или из госконтракта; ЕГРЮЛ через DaData (`DADATA_API_KEY`, кеш 30 дней): статус, возраст, отметка о недостоверности; подозрительно низкая цена снижает доверие. Кнопки «Проверен» / «Не работаем» действуют во всех закупках;
- ранжирование: успевает к сроку → соответствует ТЗ → доверие ≥ `SELLER_TRUST_THRESHOLD` → минимальная полная стоимость. Лучшее подходящее подставляется в калькулятор автоматически; выбранное вручную не перезаписывается.

**Ограничения и этика:** не обходим капчу, авторизацию и запреты robots.txt; не чаще одного запроса к сайту в `FETCH_MIN_INTERVAL_MS`; лимиты `SEARCH_MAX_API_REQUESTS` / `SEARCH_MAX_PAGES` останавливают поиск с сообщением. Решение о покупке — за человеком: перед оплатой запросите у продавца счёт и проверьте реквизиты.

## Выгодность закупки (этап 3)

**Своя цена предложения.** На шаге «Расчёт» в первом шаге есть поле «Ваша цена предложения» — всегда, а не только когда заказчик цену не назвал. Если цена заказчика есть, своя цена не может быть выше неё и равносильна снижению на торгах: в `overrides` сохраняется `price`, а `decline_pct` считается из неё (`server/tenders/details.js`, признак `inputs.own_bid`); цена и процент не расходятся — действует то, что меняли последним (`lead` в `POST /api/tenders/:id/economics`). Под шагами — таблица «Что будет при другой цене» (`priceVariants` в `server/tenders/economics.js`, поле `economics.price_variants`): цена заказчика без снижения, −5%, −10%, −15%, текущая цена и самая низкая с минимальной прибылью; считается той же функцией `calculate` и не сохраняется.

- Карточка закупки: `#tender/<id>` (ссылка «Выгодность и позиции →» в ленте).
- **Позиции**: 44-ФЗ — из извещения (`purchaseObjectsInfo`, включая лекарства), 223-ФЗ — из лотов. Если структурированных позиций нет, а документация уже разобрана — позиции извлекаются из текста ТЗ нейросетью (промпт `server\analyze\prompts\items.md`).
- **Рыночный ориентир**: контракты 44-ФЗ за год с тем же кодом КТРУ/ОКПД2 (ГосПлан `/fz44/contracts`), цена за единицу из строк контракта: медиана, минимум, 25-й перцентиль. Типичное снижение на торгах считается только по конкурентным закупкам (закупки у единственного поставщика исключаются) и только если их хотя бы три. Список поставщиков, выигрывавших такие контракты, — готовые кандидаты для поиска товара.
- **Цена закупки** для расчёта: ручная → из поиска поставщиков (этап 4) → 25-й перцентиль контрактов → «нет данных».
- **Калькулятор** (`server\tenders\economics.js`, чистые функции): у каждой цифры в интерфейсе подписано, откуда она (извещение / разбор документации / контракты ЕИС / ручной ввод / профиль). Ручные значения сохраняются для закупки.
- **Настройки экономики** — вкладка «Профиль», блок «Экономика». Значения по умолчанию — допущения, **их нужно проверить с бухгалтером**:

  | Настройка | По умолчанию | Что проверить |
  |---|---|---|
  | Налоговый режим | УСН «доходы» 6% | ваш режим |
  | НДС | 22% | актуальная ставка на 2026 год |
  | Налог на прибыль (ОСН) | 25% | актуальная ставка |
  | Стоимость денег | 20% годовых | ставка вашего кредита / депозита |
  | Комиссия банковской гарантии | 3% годовых | тарифы вашего банка |
  | Плата площадке победителем | 1%, не более 5 000 ₽ | тарифы вашей площадки (для СМП может быть ниже) |
  | Снижение на торгах | 10% | опыт в вашей нише |
  | Логистика | 5% от закупки | ваши тарифы доставки |
  | Минимальная маржа / прибыль | 10% / 10 000 ₽ | ваши требования |

  Не учитываются: страховые взносы, налог на имущество и прочие детали налогообложения; для ОСН предполагается, что продавцы и перевозчики — плательщики НДС.
- Выгодность считается в фоне после синхронизации для лучших закупок (`ECONOMICS_MAX_PER_SYNC`), для остальных — при открытии карточки. Тестовый сервер ГосПлан сильно ограничивает частоту запросов — для него см. щадящие настройки в `.env.example`.

## Скачивание документации из ЕИС и сертификат Минцифры

Кнопка «Разобрать документацию» скачивает файлы с `zakupki.gov.ru`. Сайт ЕИС (как и GigaChat) использует сертификат НУЦ Минцифры, которого нет в стандартном хранилище Node.js.

Сертификаты уже лежат в папке `certs\` (скачаны с официального сервера Госуслуг, ссылки — на https://www.gosuslugi.ru/crt):

- `russian_trusted_root_ca.pem` — Russian Trusted Root CA, действует до 27.02.2032;
- `russian_trusted_sub_ca.pem` — Russian Trusted Sub CA, действует до 06.03.2027 — **после этой даты скачайте новый** с https://gu-st.ru/content/lending/russian_trusted_sub_ca_pem.crt.

При старте сервер добавляет все `*.pem`/`*.crt` из `certs\` к стандартным доверенным сертификатам (в логе: `[certs] добавлены доверенные сертификаты`). Проверка сертификатов не отключается — просто появляется доверие к УЦ Минцифры. Другая папка — переменная `EXTRA_CA_DIR`.

Если скачивание всё же не удалось, разбор завершится понятной ошибкой со ссылкой на закупку в ЕИС — файлы можно скачать вручную и загрузить в «Разбор документации».

## Контакты поставщиков

У каждого предложения в карточке закупки — как связаться с поставщиком и ссылка на сам товар (`serverofferscontacts.js`):

- **Магазин из интернета**: телефон, почта и ссылка «Контакты» берутся со страницы товара; если телефона там нет — со страницы «Контакты» или главной (один заход на сайт, кеш по домену на 30 дней, robots.txt соблюдается). Ссылка «товар на … →» ведёт на страницу товара.
- **Поставщик по госконтракту**: телефон и почта — из карточки контракта в ЕИС (`suppliersInfo.supplierInfo.…otherInfo.contactPhone / contactEMail`), копятся по ИНН в таблице `sellers`. Сайта в реестре нет: если почта на собственном домене — показывается он, иначе ссылка «найти сайт» (поиск по названию и ИНН). Ссылка «контракт в ЕИС →» — контракт, по которому товар поставляли.
- У предложений, найденных раньше, контакты дозаполняются при открытии карточки: `POST /api/tenders/:id/contacts` (по 8 предложений за вызов, сначала выбранные и подходящие).
- Контакты и ссылка на товар попадают и в уведомление в Telegram.

## Уведомления о выгодных закупках

Чтобы не просматривать всю ленту, сервис сам сообщает о закупках с подтверждённой прибылью (`server	endersalerts.js`). Условие: вердикт расчёта «выгодно», цены всех позиций — от найденных поставщиков того же товара или введены вручную, срок подачи не прошёл. Проверка — раз в минуту, по каждой закупке одно уведомление.

- На сайте — вкладка «🔔 Уведомления»: новые (выделены, число на вкладке и в заголовке страницы) и вся история с прибылью на момент уведомления; фильтры «Новые» и «Ещё выгодны», отметка «Прочитано» хранится на сервере. Пока сайт открыт, новая закупка всплывает карточкой в углу, при разрешении — уведомлением браузера. Работает и без Telegram.
- В Telegram — сообщение с прибылью, маржой, сроком подачи, основанием расчёта по позициям и ссылкой на карточку. Нужны `TELEGRAM_BOT_TOKEN` и `TELEGRAM_ALLOWED_CHAT_IDS`; ссылка в сообщении строится от `PUBLIC_BASE_URL`. Проверить: кнопка «Прислать проверочное» на вкладке «Уведомления» или `POST /api/alerts/test`.
- API: `GET /api/alerts`, `POST /api/alerts/read` (`{ids: […]}` или `{all: true}`).

## Telegram-дайджест

1. Создайте бота у [@BotFather](https://t.me/BotFather) командой `/newbot`, скопируйте токен в `TELEGRAM_BOT_TOKEN`.
2. Запустите сервер, напишите боту `/start` — он ответит вашим chat id. Добавьте его в `TELEGRAM_ALLOWED_CHAT_IDS` (несколько — через запятую) и перезапустите сервер.
3. Каждый день в `DIGEST_TIME` (часовой пояс `DIGEST_TZ`) бот присылает закупки с оценкой не ниже порога из профиля, найденные с прошлого дайджеста. У каждой — кнопки «Разобрать» (запускает разбор документации и присылает результат) и «Не интересно» (скрывает закупку).

Команды: `/digest` — дайджест сейчас, `/sync` — загрузить закупки сейчас, `/help`. Бот работает через long polling — публичный адрес не нужен. Ссылки в сообщениях ведут на `PUBLIC_BASE_URL` (по умолчанию localhost — открываются только на этом компьютере).

## Подключение нейросети

В `.env` выберите `LLM_PROVIDER` и заполните его блок (все переменные описаны в `.env.example`).

| Провайдер | Что заполнить |
|---|---|
| `mock` | ничего — правила-регулярки, для демонстрации и тестов |
| `openai-compatible` | `LLM_BASE_URL`, `LLM_MODEL`, при необходимости `LLM_API_KEY` (Ollama, vLLM, LM Studio, OpenRouter, DeepSeek) |
| `gigachat` | `GIGACHAT_AUTH_KEY`, `GIGACHAT_SCOPE`, `GIGACHAT_MODEL` (сертификат Минцифры уже в `certs`) |
| `yandexgpt` | `YANDEX_API_KEY`, `YANDEX_FOLDER_ID`, `YANDEX_MODEL` |

Промпты лежат в `server\analyze\prompts\*.md` (`extract`, `resolve`, `summary` — разбор документации; `score` — оценка закупок) и читаются при каждом вызове — их можно править без перезапуска.

Длинная документация режется на фрагменты по `LLM_MAX_CHARS_PER_CHUNK` символов (для моделей с контекстом 32k токенов подходит 24000, для 8k — около 6000). Закупки оцениваются пачками по `SCORE_BATCH_SIZE`.

## Ограничения

- Сканы без текстового слоя, изображения, RAR, 7z не разбираются (DOC и RTF читаются: word-extractor и встроенный разбор RTF) — файл помечается в карточке.
- Один профиль компании, нет авторизации: сервис рассчитан на локальный запуск.
- Время в ответах ГосПлан приходит без часового пояса: для 44-ФЗ оно трактуется как UTC, для 223-ФЗ — как московское (по сравнению с временем создания записей; не подтверждено документацией — см. `server\sources\normalize.js`).
- Оценки и рекомендации — подсказка, решение принимает человек.
