# Задание для Quod: мебельные поставщики и точный подбор по полному ТЗ

Дата: 23 октября 2026. Это дополнение к действующей платформе анализа закупок.

## Цель и границы изменения

Подключить мебель к существующему поиску: извлекать все условия каждой позиции и общие условия закупки, находить кандидатов, дочитывать недостающие характеристики на сайтах изготовителей, в паспортах, инструкциях, чертежах и приложениях, затем проверять конкретное исполнение. Выбирать выгодное предложение можно только после этой проверки.

Проблема чтения 80% уже исправлена пользователем. Последние улучшения поиска сделаны совместно с Quod; их исходный код в этом исследовании не представлен. Не возвращать старые ограничения, не переустанавливать прежний поисковый пакет и не переписывать рабочие коннекторы. Начать с текущего кода и тестов. Архивные пути `server/offers/*`, `supplier-catalog`, `site-index`, `sitemap` — ориентиры, существование и актуальность проверить в репозитории.

Пакет содержит 42 источника поставщиков, 8 каналов расширения, 16 профилей мебели, словарь, поисковую политику, пример контракта данных и проверочные сценарии. Это готовые исходные данные для интеграции, но не развернутые коннекторы. Исследование не включает доступ к серверу, фактическое мебельное ТЗ пользователя, коммерческие переговоры или закупку.

## 1. Импортировать источники без повреждения текущей базы

Использовать `config/furniture-suppliers.json`. Выполнить dry run с числом добавлений, совпадений и конфликтов; затем идемпотентный импорт. `id` в этом пакете — идентификатор источника/бренда; он не доказывает существование отдельного независимого юридического лица.

Сохранить существующие идентификаторы `felix`, `promet`, `samson`, `sima`, `komusopt` и каналов. Сохранить старые мебельные маршруты `prist` и `apexmed`, если они разрешены действующей конфигурацией. Не удалять другие категории. Новые профили сделать дочерними для `furniture`; медицинскую и лабораторную мебель связывать также с действующими профильными категориями, не дублируя товар и предложение.

Объединять источники по подтвержденным реквизитам/связи доменов, а не по похожему названию. «Бюрократ» — источник заводских характеристик, MERLION — связанный B2B-канал; БюроКресла — отдельное предложение продавца. ПРАКТИК не новый завод относительно ПРОМЕТ. `paksmet.ru` и `paks-met.ru`, `stolprom.com` и `stolprom.ru` не считать одной компанией без подтверждения. Разделить `manufacturer`, `brand`, `supplier_legal_entity`, `source`, `offer`.

По каждому источнику хранить профиль мебели, каталог, страницы документов/сотрудничества, статус доступа, дату проверки, приоритет подключения. Не заполнять неизвестные минимальную партию, остаток, цену опта, НДС и сроки предположениями. Не импортировать маркетинговое заявление «соответствует всем ГОСТ» как доказательство соответствия позиции.

Приоритет 1 означает очередность интеграции. Это не рейтинг качества поставщика. Девять источников с 403, таймаутом, 502 или пустой JS-страницей остаются маршрутами обнаружения до успешной проверки разрешенного чтения. Не выдавать их за готовые парсеры. Публичное чтение страницы через исследовательский инструмент не гарантирует доступ с IP сервера.

## 2. Сформировать полный набор требований мебели

Применить `config/furniture-profiles.json` и `furniture-aliases.json` как расширяемые подсказки. Перечень полей никогда не должен ограничивать количество требований ТЗ. Незнакомое свойство сохраняется с исходным текстом и собственным ключом.

Для каждой закупки собрать перечень всех файлов, редакций и приложений: ТЗ, спецификация, таблицы, проект договора, схемы, чертежи, изменения. Сначала установить действующую редакцию и связи документов. При неоднозначности приоритета документов выставлять конфликт, не выбирать удобную редакцию молча.

Извлекать данные из PDF/DOCX/XLSX, включая объединенные ячейки, переносы таблиц, сноски, примечания, текст на рисунках. Для изображений и страниц без пригодного текстового слоя — OCR и чтение схем. Сохранять документ, страницу, таблицу/строку/ячейку либо координаты области, исходный текст, единицу, оператор, область применения. Ключевые цифры и знаки `≥`, `≤`, диапазоны после OCR проверять повторно по изображению; не выдавать уверенность модели за доказательство.

Расщеплять составные строки на атомарные требования. Например, «ЛДСП 18 мм, кромка ПВХ 2 мм по лицевым торцам» содержит как минимум материал плиты, толщину плиты, материал кромки, толщину и область применения кромки. Связь с исходной строкой сохранить. Общие требования распространять на подходящие позиции с явной ссылкой на исходное общее условие, не теряя исключения.

После извлечения выполнить независимый проход полноты: все страницы и таблицы прочитаны; каждый содержательный пункт ТЗ либо связан с требованиями, либо имеет обоснованное назначение (заголовок, справочная информация, исключенное условие). Сверить перечень позиций, единиц и количеств. Пустая таблица, непрочитанный рисунок, недостающий файл или пропущенная строка запрещают `coverage_complete`. Противоречия между таблицей, текстом и чертежом показать отдельно.

Классифицировать требования: технические; состав/комплектность; документы/происхождение при применимости; коммерческие; доставка и услуги. Все группы остаются в результате. Технические 100% не означают готовность сделки, если неизвестен срок, количество или монтаж.

## 3. Искать кандидатов и дочитывать недостающие поля

Использовать текущий поисковый провайдер и его действующий бесплатный режим/квоту. Не добавлять платный Яндекс Search API или иной платный сервис автоматически. Публичная информация может быть бесплатной, но обработка, OCR, браузер и сервер имеют ресурсную стоимость. «Весь интернет бесплатно без лимитов» не является обеспечиваемой возможностью.

Маршрут: текущий индекс и кэш → профильные фабрики/оптовики → разрешенные выгрузки → открытый веб-поиск → документы изготовителя → существующие коннекторы маркетплейсов → поиск новых фабрик в каталогах отрасли. Повторно использовать действующие sitemap/site-index/reader, если они уже работают. Роботов, ограничения сайтов и защиту не обходить. Для отсутствующего API не выдумывать URL; сохранять `null` и использовать доступную страницу или согласованную выгрузку.

Без модели в ТЗ искать по назначению и наиболее различающим ограничениям: вид изделия, ключевой размер, материал, регулировка, число секций. Не требовать артикул как условие начала поиска мебели. Категория направляет поиск, а соответствие устанавливается по требованиям.

Когда найден товар у продавца, выделить изготовителя, артикул, серию, исполнение, цвет, сторону, размеры, обивку, механизм, комплектацию. Создать `variant_fingerprint`; цена привязывается к тому же варианту. Затем искать точную модель/артикул и каждое незакрытое поле в первичных источниках. Нормализовать пробелы/дефисы осторожно; `523`, `523м`, `523 ЭКО` и разные размерные исполнения — не один SKU.

Дочитывать не только блок «Характеристики», но описание, вкладки, таблицы размеров, комплектность, PDF, инструкции, схемы сборки и технические приложения. Не брать параметры соседних товаров, рекомендаций или невключенных опций. Страница с выбором нескольких исполнений требует привязки выбранных значений; «может комплектоваться» не равно «входит в поставку».

Значение из другого источника переносить только при доказанной применимости к модели и исполнению. Серийное свойство допустимо наследовать лишь при явном подтверждении для всех нужных исполнений. Если продавец не указал артикул/исполнение, продолжать установление личности товара; не склеивать характеристики похожих моделей в идеальный несуществующий товар.

Сохранять для каждого факта URL, дату получения, хеш документа, версию, место в документе, короткий фрагмент и способ чтения. Разделять: факт найден; источник подтверждает факт; факт относится к варианту; факт соответствует требованию. Любая из этих проверок может не пройти.

При расхождении источников установить, не относятся ли они к разным версиям/исполнениям. Если это доказано — разделить версии и сравнить нужную. Если нет — `conflict`, не выбирать значение по большинству сайтов. Даже официальный паспорт другой ревизии не разрешает конфликт автоматически. Один точный первичный источник может быть достаточен; две перепечатки продавцов не заменяют доказательство.

Не завершать всю процедуру после первого найденного продавца. Для цены собирать несколько доступных предложений на подтвержденный вариант; если предложение только одно, показывать это. Если бюджет запросов исчерпан, сохранить прогресс, незакрытые требования и конкретные следующие запросы. Статус `continuation_required`, не «товар соответствует» и не «во всем интернете товара нет».

## 4. Правила, которые особенно важны для мебели

| Объект | Правило |
|---|---|
| Размеры | Различать Ш/Г/В, длину, диаметр, габарит изделия, столешницу, сиденье, спальное место и упаковку. Не сортировать три числа. Строка `510×585×850` без порядка осей не доказывает ширину 510. |
| Операторы | Точно = точно; ≥ и ≤ сохраняют направление. Допуск только из применимого требования/документа. Не применять самовольные ±5%, ±20 мм или «больше — лучше». |
| Производственный допуск | Если реальный размер имеет интервал, для автоматического pass весь гарантированный интервал должен удовлетворять ТЗ. Допуск производителя не расширяет разрешенный диапазон заказчика. |
| Регулировки | Дискретные положения отличаются от непрерывного диапазона. Наличие 520/580/640 мм не подтверждает любую высоту между ними. Ростовая группа — отдельный параметр изготовителя. |
| Материалы | ЛДСП, МДФ, фанера различны; ПВХ и ABS различны; CPL/HPL различны. Материал корпуса не является материалом столешницы. |
| Кромки и металл | Толщина лицевых торцов отдельно от остальных; толщина металла отдельно от размера трубы, столешницы и крепежного винта. |
| Обивка | Лицевые, боковые и задние части раздельно. Категория ткани, цвет и износостойкость относятся к выбранному образцу, не ко всей серии. |
| Нагрузка | На пользователя, место, полку, ящик, верстак, секцию — разные поля. Статическая, распределенная и рабочая нагрузки не взаимозаменяемы. |
| Комплект | Проверять спецификацию BOM по каждому компоненту и количеству. Стол с тумбой не равен столу без тумбы; цена «от» не цена выбранного комплекта. |
| Кровати | Габарит, спальное место, ярусы, основание, лестница, ограждения, матрас и нагрузка на ярус проверяются отдельно. |
| Документы | Проверять применимость к изделию/материалу/партии и действительность. Назначение «для больницы» само по себе не определяет необходимость регистрационного удостоверения; брать применимые условия закупки и действующие правила платформы. |
| Цвет | Согласованный код/название/образец; не устанавливать точный RAL по фотографии или цветопередаче монитора. |

Для мебели по заказу создать отдельный тип `custom_manufacturing_candidate`. Заявление «изготовим по вашим размерам» подтверждает только возможность запроса. Для подтверждения нужны зафиксированные изготовителем спецификация/чертеж/BOM, выбранные материалы и исполнения, цена и срок на этот состав. До этого не ставить 100%. Можно автоматически подготовить черновик матрицы вопросов; отправка поставщику выполняется только по отдельному разрешенному действию пользователя.

## 5. Статусы и честные 100%

На каждом обязательном требовании: `pass`, `mismatch`, `unknown`, `conflict`. `not_applicable` допустим только с проверяемым основанием и явным исключением в условиях; нельзя повышать процент, исключая неудобные требования. Неразобранное условие сохраняется и блокирует pass.

`technical_100` разрешен только если набор требований не пуст, подтверждена полнота документов и извлечения, определено точное исполнение, каждое обязательное техническое требование имеет применимое доказательство и статус pass, нет неразрешенных конфликтов. Никакой порог 80/90/95% этого не заменяет. Низкая цена и рейтинг поставщика не компенсируют несовпадение.

Отдельно показывать:

- полноту обработки документов: страницы/таблицы/вложения и проблемы чтения;
- полноту извлечения по контрольной разметке ТЗ, когда она есть;
- долю требований с применимыми найденными данными;
- долю подтвержденных совпадений, число несовпадений, неизвестных и конфликтов;
- готовность документов, количества, срока, доставки и услуг.

Если независимо проверенного перечня требований нет, не называть отношение «обработано 10 из 10 страниц» доказанной стопроцентной точностью извлечения. Цель — стремиться к полному охвату и не пропускать неподтвержденные товары в группу соответствующих.

Вывод по позиции: требование → найденное значение → выбранный вариант → источник/страница → результат → причина/следующее действие. Для пользователя неизвестное значение должно сопровождаться причиной: не опубликовано, неоднозначное исполнение, документ не прочитан, источник закрыт, конфликт версий или поиск еще не завершен.

## 6. Сравнение стоимости

Сравнивать доступные предложения на одну подтвержденную комплектацию и нужное количество, с одинаковой базой учета НДС. Использовать действующие правила платформы, ставку не зашивать константой. Добавить доставку, упаковку, подъем, сборку, монтаж, необходимые крепления/расходники и прочие обязательные услуги. Неизвестные расходы не равны нулю. Учитывать минимальную партию, актуальность остатка, срок изготовления/доставки, гарантию и территорию обслуживания.

Сохранять источник и момент цены. Публичная розничная цена не подтверждает оптовую; «цена по запросу» не означает нулевую. Общий рейтинг выгодности считать после технических и обязательных документальных проверок. При неизвестной полной стоимости допустим статус «предварительное предложение», но не «самая выгодная подтвержденная закупка».

## 7. План внедрения в имеющийся лимит работы

Ниже ориентир на прежний восьмичасовой бюджет внедрения, не обещание длительности и не разрешение пропускать проверки.

| Блок | Ориентир | Проверяемый результат |
|---|---:|---|
| Осмотр актуального кода и baseline | 0,5 ч | Найдены действующие импортер, поиск, reader, сопоставление, фоновые задания; сохранены текущие результаты |
| Импорт и маршрутизация | 1 ч | 42 источника и 8 каналов загружаются без дублей; 16 профилей доступны поиску |
| Подключение первых источников | 1,5 ч | Реальный проход минимум по Росметалл, CHAIRMAN, Феррум, одному офисному и одному лабораторному каталогу; ограничения записываются |
| Полнота ТЗ, варианты и дочитывание | 2 ч | Неизвестное свойство инициирует адресный поиск; PDF/OCR и сноски участвуют; неподтвержденные варианты блокируются |
| Регрессия и реальные ТЗ | 2 ч | Контрактные сценарии и ранее проблемные позиции проходят, нет ложных pass |
| Итог и переключение | 1 ч | Отчет до/после, очередь незакрытого, функция включения/отката и журнал миграции |

Переиспользовать готовые функции. Не писать по отдельному браузерному парсеру на все 42 сайта до работающего прохода на первых источниках. Остальные источники подключать через универсальные публичные карточки/документы и действующий поиск с последующей проверкой. Наличие источника в реестре не засчитывать как успешный end-to-end поиск.

## 8. Приемка

1. `node tools/validate-kit.mjs` проверяет структуру самого пакета. Это не тест качества платформы.
2. Сценарии `tests/acceptance-cases.json` выполнить на текущем парсере/матчере через тонкий адаптер либо существующие тесты. Записать фактические результаты в согласованном JSON и проверить `node tools/check-contract-results.mjs /absolute/path/actual-results.json`. Не копировать ожидаемые ответы в фактические результаты. Результат без выполнения помечать `not_executed`.
3. Повторить исследовательские примеры из `research/live-pilot.json`: карточка + сноска, инструкция без текста + OCR, выбор исполнения школьного стола, подробное описание медицинского стола. Они проверяют чтение данных, но не заменяют реальное ТЗ.
4. Использовать минимум пять реальных мебельных ТЗ пользователя из доступных данных платформы, включая ранее не найденные позиции; при отсутствии отметить блок как не выполненный. Контрольный перечень требований сверить с исходными документами. Минимум один случай >45 требований, скан, таблица со сноской, вариантный товар и заказное изделие.
