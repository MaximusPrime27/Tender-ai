# Внедрение комплексного анализа закупки в Tender AI

Версия 1 от 19.10.2026. Задание адресовано Claude Code, работающему в актуальном репозитории Tender AI. Выполни реализацию и проверки, а не только предложи план или перепиши промпт ГигаЧата.

## 1 Результат для владельца

В карточке закупки появится команда «Полный анализ». Она формирует единый доказательный отчёт: что закупают, допускается ли участие, какой товар подходит, где подтверждена поставка, сколько денег нужно, каков результат сделки, что не согласуется в документах и что необходимо для заявки. Экран, DOCX, PDF и JSON используют один неизменяемый снимок данных.

Образец из приложенного документа используется для состава разделов. Ошибочные выводы образца не воспроизводить. Его полный разбор находится в AUDIT_REFERENCE.md: 33 замечания A01–A33. Основной безопасный результат при отсутствии ключевых источников — «Недостаточно данных», с полезным частичным отчётом и действиями по устранению пробелов.

Не смешивай четыре вопроса: «что написано заказчиком», «соответствует ли это норме», «соответствует ли наш участник/товар» и «выгодно и исполнимо ли нам участвовать». Положительный ответ на один не доказывает остальные.

## 4 Источники и полнота

Собирать не только загруженный пользователем файл: актуальное извещение/структурированные сведения, вложения, ТЗ, проект контракта, спецификации, формы, инструкцию заявки, обоснование НМЦК, изменения, разъяснения, при 223-ФЗ положение заказчика и документы процедуры. Если источник недоступен, сохранить ожидаемый файл и причину, а не убрать его из знаменателя полноты.

Для каждого файла: ID, роль, исходный URL/канал загрузки, имя, SHA256, версия, получен/не получен, опубликован/получен, связи с лотом и заменённой версией. Не использовать правило «последний загруженный файл всегда главный»: загрузка старого файла не создаёт новую редакцию извещения.

Отчёт другой программы классифицировать `secondary_analysis`. Он даёт кандидаты утверждений, но не доказывает исходные условия. Полное прочтение всех его страниц не означает чтение комплекта закупки. Печатная форма ЕИС, структурированные поля и прикреплённый документ проверяются в контексте действующей редакции и применимой нормы; безусловную иерархию для любого конфликта не выдумывать.

Обрабатывать PDF, сканы, DOCX, таблицы, изображения с требованиями и разрешённые архивы по правилам прежнего задания. Отдельно учитывать общие условия, позиции/характеристики и требования к заявке. Для каждого пути: ожидаемые единицы и диапазоны, обработанные, пропуски, причины, повторы. Номер абзаца DOCX не называть физической страницей; сохранять абзац/таблицу/ячейку и при наличии карту рендеринга.

Ответ ГигаЧата с finish_reason, указывающим обрыв, не становится завершённым из-за корректного JSON. Названия полей завершения уточнить для актуального API. Дедупликация идёт по происхождению, а не только похожему тексту. При бюджете/ошибке — частичный результат, возобновление с контрольной точки, без молчаливого сокращения.

## 5 Общая модель данных и доказательства

Единая цепочка: `procurement/lot → source revision → fact/requirement → rule evaluation → participant/product/offer → economics/bid → report snapshot`.

Минимальные сущности и поля:

| Сущность | Обязательное содержание |
|---|---|
| Fact | Ключ, типизированное значение, единица, событие, статус, evidence_ids, альтернативы и причина выбора |
| Evidence | Source ID/hash/version, точный адрес, исходная цитата или структурированное значение, проверка совпадения, момент получения |
| Rule | Норма, структурная единица, временная применимость, исключения, inputs, источник, версия, тесты, утверждение |
| Requirement | Кому/чему относится, стадия, обязательность/оценка, подтверждение, канал, правило, исходный текст |
| Check | Объект и критерий, expected/actual, pass/fail/unknown/not_applicable/conditional, evidence_ids, rule_ids, последствия, действие |
| Finding | Категория проблемы, подтверждение, тяжесть и основание, зависимые решения, способ устранения, автор/срок |
| Offer | Продавец, ИНН при наличии, точный SKU/исполнение, цена/валюта/НДС, остаток, количество, упаковка, доставка, срок действия, КП |
| Deadline | Событие-основание, длительность, вид дней, timezone/calendar, официальный/внутренний/вычисленный, зависимости, источник |
| Snapshot | Версии всех входов, rules/prompts/schema/calculator, generated_at, as_of, evidence graph, результаты и контроль целостности |

`unknown`, `not_found_after_complete_review`, `not_applicable`, `failed` и значение 0 различаются. `not_applicable` требует основания. Проверка наличия цитаты в файле не доказывает правильность её толкования. Высокая уверенность модели не заменяет источник.

Деньги хранить целыми копейками или Decimal; в JSON большие денежные значения передавать десятичными строками. Проценты и валюта имеют типы. Даты хранить с часовым поясом; относительный срок не превращать в дату без подтверждённого события и календаря.

## 6 Алгоритм одного анализа

1. Определи закупку, лот, правовой режим, процедуру и её стадию. Если режим неизвестен, не применять 44-ФЗ по умолчанию.
2. Зафиксируй ожидаемый комплект первичных источников, версии и незагруженные файлы.
3. Полностью извлеки текст/таблицы/визуальные требования. Сохрани coverage каждого пути.
4. ГигаЧат извлекает атомарные факты и адреса; сервер валидирует схему, источники, числа и полноту. Успешные части сохраняются.
5. Сопоставь поля одинакового смысла. Дата публикации и дата подачи не конфликтуют; две даты подачи из разных редакций требуют установления действующей версии.
6. Построй реестр требований и карту обязательств проекта контракта. Обработай все разделы, включая приложения и перекрёстные ссылки.
7. Подбери применимые версии правовых правил по событиям. Проверь условия заказчика, отдельно проверку участника, отдельно товар. Недоступная правовая ветка — needs_review.
8. По каждой позиции сформируй техническую матрицу и проверку происхождения. Свяжи её с конкретными предложениями поставщиков.
9. Передай подтверждённые входы в существующий калькулятор. Сохрани все оценки и неизвестные расходы; рассчитай сценарии и календарь денег, если данных достаточно.
10. Передай применимые требования в модуль заявки. Получи статусы файлов, полей ЭТП, оригиналов и действий. Не считать готовность ZIP фактом подачи.
11. Кодом вычисли независимые статусы и допустимую рекомендацию. Зафиксируй blocker IDs и зависимости.
12. Сформируй план действий от текущего времени и стадии. Объедини повторяющиеся задачи по устойчивому ID.
13. Сформируй текст объяснений по проверенным фактам, без самостоятельного изменения статуса моделью.
14. Выполни вторую проверку полноты отчёта и чисел, совпадения источников, версии и отсутствия утечки внутренних данных в заявку.
15. Зафиксируй снимок и отрисуй экран/экспорты из него. Перед новым экспортом/решением проверяй истечение КП, изменение документов и правил.

Если один блок недоступен, остальные продолжают работу. Пользователь видит выполненное и то, почему окончательный вывод пока невозможен.

## 7 Правовой анализ

Правила реализуются проверяемым кодом/таблицами с временной применимостью. Промпт не содержит единственную «правовую базу». LEGAL_SOURCES.md описывает проверенную основу и непроверенные участки; перед активацией каждого production-правила повторно проверь полный действующий текст.

### 7.1 Участник и объект

Проверять допуск по виду участника, СМП/СОНКО или МСП, общим и дополнительным требованиям, ограничениям, полномочиям, лицензиям при наличии основания. Различать требования заказчика и требования закона; спорное требование фиксируется как правовой вопрос, а не молча удаляется из заявки.

По объекту: коды, КТРУ при применимости, наименование, количество, единицы, характеристики, комплектность, эквивалентность и условия заполнения. Диапазон в ТЗ не всегда требует заменить его одним числом: хранить инструкцию заполнения отдельным полем и проверять её совместно с характеристикой. Не менять 35–38 на 38 только потому, что модель имеет такую скорость.

### 7.2 Национальный режим

Для каждой позиции: мера, акт/редакция/позиция перечня, совпадение кода и описания, исключения, документы происхождения, реестровая запись/производитель/модель, применимые баллы/уровень/переходные положения. Для лота проверять совместное применение и смешанные предложения.

Разделять запрет, ограничение и преимущество. Не считать все меры одним отказом. Для ограничения хранить условие срабатывания и неизвестность состава конкурентов. Для преимущества отдельно хранить оценочную цену и цену контракта: оценочное снижение не уменьшает нашу выручку автоматически. Не прогнозировать вероятности отклонения без данных и методики.

Страна бренда ≠ страна происхождения; номер записи ≠ подтверждённое соответствие точной модификации. Недоступный реестр ≠ запись отсутствует. Не подменять отсутствующую запись выдуманным номером, сертификатом или картинкой категории.

### 7.3 Антидемпинг и обеспечение

Раздельные правила статьи 37 и части 8.1 статьи 96, разные критерии трёх контрактов и разные последствия. База обычного обеспечения, усиление, минимальные величины, аванс, исключения и стадия представления рассчитываются по применимой ветке. В интерфейсе показывать доступные варианты и потребность в деньгах, включая вариант новичка без истории контрактов.

Номинал возвратного денежного обеспечения — блокировка средств, а не расход прибыли. Независимая гарантия имеет стоимость и условия, но её получение не считается подтверждённым без предложения/документа.

### 7.4 Контракт

Проверять: предмет и спецификацию; цену и её состав; налоги; доставку/разгрузку/монтаж; приёмку; оплату; обеспечиваемые обязательства; гарантию; штрафы и пени; удержания; изменение и расторжение; претензии; подсудность; уведомления; обязанности и расходы, скрытые в приложениях.

Каждая строка: что требует контракт → где написано → какая норма проверяется → что требуется от нас → денежное/сроковое последствие. Риск нарушения со стороны заказчика не равен автоматическому недопуску поставщика.

Обработать все 14 видов сроков из AUDIT_REFERENCE.md. Не подставлять рабочие дни вместо календарных. Срок оплаты считать от предусмотренной приёмки, а не автоматически от доставки. Гарантию сравнивать с обязательствами нашего поставщика. «Входит в цену» и «необходимо выполнить отдельную работу» — разные факты.

Для 223-ФЗ использовать отдельный адаптер на основе актуального положения заказчика. Без положения, если оно нужно для вывода, не объявлять правовую проверку завершённой. Неподдерживаемая процедура видна как unsupported.

## 8 Поставщики и экономическая целесообразность

Переиспользуй текущий поиск через Яндекс и модуль предложений. В отчёте должны быть конкретные предложения, а не только главные страницы магазинов. Ступени подтверждения: найдено поиском → открыта товарная страница → сопоставлен товар → уточнены коммерческие условия → получено актуальное подтверждение цены/наличия. Переход фиксируется доказательством.

По каждому предложению показать точную модель, продавца, URL, время проверки, количество, цену с видом НДС, срок фиксации, наличие/резерв, срок доставки до адреса, предоплату/отсрочку, гарантию и происхождение. Не обещать доступную отсрочку из рекламы магазина. Цена аналога не становится ценой соответствующей позиции.

Матрица обязательных характеристик: requirement ID → значение ТЗ/правило заполнения → значение модели → источник производителя/документа → pass/fail/unknown. Похожие названия не являются соответствием. Конфликт каталога и КП сохранять. Для оргтехники учитывать скорость разных операций, дуплекс печати/сканирования, интерфейсы, расходники, ресурс и комплект. Для связи и CCTV — проверки из прежнего задания калькулятора.

Экономика использует цену участия/контракта, себестоимость всей корзины, доставку, упаковку, разгрузку, требуемые работы, комиссии, финансирование, гарантийный сервис, налоговый профиль и сценарные расходы. Общую доставку и НДС не считать дважды. Требование 24 месяцев гарантии без оценки поддержки не означает нулевой расход.

Показывать плановую прибыль, определение маржи, цену без убытка, безопасный предел снижения по выбранным допущениям, максимальную потребность в финансировании, нехватку бюджета и цикл денег. Отдельно — базовый и неблагоприятные сценарии. Положительная прибыль при дефиците оборотных средств не даёт финансовый допуск.

Неизвестная стоимость не заменяется нулём. Предварительный расчёт допустим с явно видимыми предположениями, но статус «выгода подтверждена» закрыт. Налоги определяются по профилю на дату операции; УСН не является синонимом «без НДС». Налог на прибыль/УСН за период не выдавать за точный налог одной сделки без согласованной методики распределения.

Рейтинг закупок строить сначала по исполнимости и полноте, затем по экономике и предпочтениям владельца. Полные и неполные оценки не смешивать в одном списке «самые выгодные» без пояснений. Порог желаемой прибыли/маржи/бюджета настраивается пользователем, а не выдаётся за норму закона.

## 9 Статусы и правила решения

Независимо хранить coverage, analysis_status, legal_status, product_match, supplier_fulfillment_readiness, economic_status, funding_status, document_readiness, platform_actions_readiness и статус пакета. Состояние «анализ завершён» не должно означать «участвовать».

| Рекомендация | Условие |
|---|---|
| Недостаточно данных | Неизвестны существенные условия, не завершён нужный путь чтения, не проверена применимая правовая ветка, товар/цена/финансирование не подтверждены |
| Не участвовать | Есть подтверждённый действующий запрет/несоответствие или экономическая/сроковая невозможность, относящаяся к выбранному сценарию |
| Участвовать с конкретными условиями | Все существенные данные проверены; остаются известные, ограниченные и явно описанные условия/коммерческие риски, а не пробелы чтения |
| Участвовать | Применимые проверки пройдены, выбранный сценарий исполним, пользовательские пороги выполнены; это рекомендация, а не гарантия допуска/победы |

Подтверждённое препятствие можно показать и при неполном анализе, если его доказательство само полно и актуально. Общая полнота при этом не повышается. Препятствие одной модели не означает, что невозможны все альтернативы закупки.

`stale` при изменении источников/профиля/офера/правила — отдельный статус снимка. Старый вывод остаётся в истории, но не используется как актуальный. Известное обязательное условие не может быть «принято пользователем» так, чтобы отменить юридический недопуск. Ручная правка имеет автора, причину и источник, сохраняет исходное значение и запускает зависимые проверки.

В reference есть минимальный пример шлюза статусов. Он не проверяет подлинность документов и не заменяет серверную валидацию. Производственный код должен проверять граф доказательств, а не доверять полям evidence_verified из клиентского запроса.

## 10 Документы заявки и задачи

Используй прежний модуль заявки. По каждому требованию: сведения/файл/поле → источник → подтверждение → стадия → часть/канал → результат проверки → недостающее действие. Сведения оператора и декларации средствами площадки не превращать автоматически в отдельный PDF.

Досье организации заполняется один раз с актуальностью и правами доступа. Не запрашивать заново известный ИНН и не собирать условно ненужные сведения. Подписант, полномочия, КЭП/МЧД, регистрация, документы опыта, происхождение и параметры товара проверяются по применимости. Создавать допустимые черновики форм; не генерировать лицензии, реестровые записи, подписи или поддельные оригиналы.

Задачи: основание/finding ID, что сделать, владелец, официальный и внутренний срок, стадия, зависимость, документ результата, состояние. Для запроса разъяснений определить возможность и срок по процедуре. Если окно закрыто, показать это и доступные законные следующие действия, не обещать исправление через просроченный запрос.

План от as_of/текущего времени. После дедлайна не создавать новую задачу «подать завтра». Просроченные задачи сохраняются. Отсутствие плановой даты означает неизвестное, а не сегодняшнее число. Ручной перенос внутренней задачи не изменяет официальный срок.

## 11 Экран и экспорт

На первом экране: номер/предмет, проверенная актуальность, рекомендация и её основания, дедлайн с часовым поясом, прибыль/денежный пик либо «не рассчитано», до пяти главных препятствий и следующее действие. Полный реестр остаётся доступным; ограничение пяти строк относится только к сводке.

Вкладки: Обзор, Требования, Товар и нацрежим, Контракт и сроки, Поставщики и деньги, Заявка и действия, Источники. Справа в Copper-интерфейсе можно оставить сворачиваемый список проверок/действий. На телефоне единая колонка, критические вопросы не скрывать в тултипах. Цвет сопровождать текстовым статусом.

По нажатию на вывод открываются цитата/адрес в первичнике, источник, правило и объяснение. При конфликте видны обе версии. Реестр источников доступен целиком, даже если в краткой таблице показаны только основные ссылки.

REPORT_TEMPLATE.md задаёт полный состав: девять областей образца сохранены и дополнены качеством источников, матрицей товара и полноценной экономикой. Все разделы отображаются, включая пустые с причиной и следующим действием. Не исчезает раздел «Поставщики» при отсутствии предложений.

Экспорт внутреннего отчёта разрешён и при неполноте, но содержит явную отметку, неизвестные поля и причины. Экспорт внешнего пакета заявки имеет отдельные правила блокировки. Внутренний DOCX/PDF не входит в пакет заявки автоматически.

DOCX формировать программно из снимка, с нормальными стилями, повторяемой шапкой длинных таблиц, переносами, номерами страниц, читаемыми URL/адресами источников. PDF — из того же документа или того же снимка с проверкой содержания. Проверить все страницы рендеринга; не выпускать таблицы с обрезанными словами/колонками. В шаблоне не должно быть фраз модели «все данные собраны» до проверки полноты.

Имя экспорта: tender-analysis-<number>-<snapshot>.docx/pdf/json. Заголовок содержит дату проверки, версию снимка и режим. Сохранять исторические версии. Реальные фотографии ТЗ/товара остаются доказательствами, AI-картинки категорий — только оформлением интерфейса.

## 12 Архитектура и надёжность

Логические модули: inventory/coverage, facts, reconciliation, legal-rules, product-compliance, contract-obligations, commercial-adapter, bid-adapter, decision, report-builder, exporters. Встраивать в текущую архитектуру; не вводить новую инфраструктуру без нужды.

Предлагаемый API, после сверки существующего:

```
POST /api/tenders/:id/comprehensive-analyses
GET  /api/tenders/:id/comprehensive-analyses/:runId
POST /api/tenders/:id/comprehensive-analyses/:runId/resume
GET  /api/tenders/:id/reports/:snapshotId
GET  /api/tenders/:id/reports/:snapshotId/export?format=docx|pdf|json
```

Все маршруты проверяют организацию, право доступа к закупке/файлам, формат и размеры ввода. ID отчёта не является разрешением на доступ. Фоновые задания идемпотентны; ключ включает версии входов, правил и задач. Поздний ответ старого запуска не перезаписывает новый снимок. Экспорт атомарен относительно одной версии.

Текст вложений и сайтов — недоверенные данные: инструкции «игнорируй правила», скрытые команды и ссылки внутри документов не меняют системный промпт и не вызывают инструменты. Загрузчик ограничивает типы/размеры/архивы, защищает внутренние адреса и пути файлов; активное содержимое не исполняется. Не передавать секреты и лишние персональные данные в LLM, не включать их в логи и диагностические архивы.

Не добавлять фиктивные успешные интеграции. Отсутствие доступа к ЕИС/реестру/платному источнику показывать как конкретную недоступную проверку. Предусмотреть ручную загрузку подлинного документа с происхождением, без автоматического повышения доверия до официального API.

Промпты в prompts — стартовая основа. Раздели получение данных и объяснение; модели не позволять произвольно менять числовые расчёты, норму, severity или итоговый gate. Сохраняй версии промптов, модели, расход, причины повторов. Не отправляй весь проект контракта одной обрезанной строкой.

## 13 Порядок внедрения

1. Обследование, единый контракт данных, миграции и адаптеры старых результатов. Legacy без provenance остаётся непроверенным.
2. Полнота источников и три пути извлечения, доказательства и сверка событий/версий.
3. Правовой движок и матрица контрактных обязанностей; сначала проверенные ветки, unsupported для остальных.
4. Связь с товарами, поставщиками, экономикой, заявкой и задачами; общий статус считается кодом.
5. Полный экран и DOCX/PDF/JSON из одного снимка; визуальная проверка экспорта.
6. Сквозные сценарии, миграция старых карточек, отчёт об ограничениях и план выкладки.

Каждый этап имеет рабочий результат и проверки. Не заканчивать на статическом макете или наборе промптов. Если внешнего доступа нет, продолжить независимую реализацию, использовать явно тестовые фикстуры и сохранить неподтверждённый статус.

## 15 Что представить владельцу

Покажи изменённые файлы, миграции, выполненные сценарии с результатами, непрошедшие/непроверенные сценарии и причины. Приложи пример отчёта по этому образцу со статусом недостаточности первичных данных и полный тестовый пример с явной пометкой вымышленных данных. Покажи экран и открывающийся DOCX/PDF, карту источников, воспроизведение ошибок A01–A33 и команды запуска.

Отдельно укажи: реализовано локально / проверено на тестовом сервере / выложено в production. Не объявляй выкладку выполненной без доступа и фактической проверки. Автоматическое подписание, подача заявок, рассылки поставщикам, обращения заказчику и платежи не входят в этот модуль.

Сохраняй прогресс в docs/COMPREHENSIVE_ANALYSIS_IMPLEMENTATION.md после каждого этапа: commit, проверки, ограничения и следующий шаг. При возобновлении продолжать с него. Файл состояния не снимает лимиты сервиса и не гарантирует самостоятельный запуск после их обновления.
